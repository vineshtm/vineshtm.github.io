Engineering in practice

The interesting part
is what happens underneath.

Building interactive products is rarely just about implementing features. Many of the problems I worked on involved the interaction between runtime performance, memory, networking, assets, platform capabilities and user experience.

01 / RUNTIME CONTENT

Bringing dynamic 3D content into Unity

Creator & Wonder

The problem

Creator needed to allow users to bring custom 3D models, images and textures into an interactive content-authoring workflow. The assets were not necessarily known at build time.

Engineering approach

A runtime asset flow was established around uploading content to the server, downloading it when required and importing the content into the Unity environment. The workflow was designed around the constraints of runtime content delivery.

What it demonstrates

Runtime asset management, dynamic content pipelines, network-aware loading and Unity editor/runtime integration.

02 / PERFORMANCE & MEMORY

Making large visual catalogues practical

ViXR Engage

The problem

Engage used catalogues containing large numbers of signage images. Large source images created problems around download size, local storage, loading time and runtime memory.

Engineering approach

Uploaded catalogue images were compressed while preserving visual quality. Lazy loading reduced unnecessary loading, while frequently required content could be downloaded once and stored locally on iPad.

What it demonstrates

Understanding the relationship between asset size, network transfer, storage, memory usage and application responsiveness.

03 / AR PERFORMANCE

Keeping AR responsive during real-time collaboration

Remote Assist

The problem

Remote Assist combined video streaming, communication and AR functionality. Mobile performance issues and low-network conditions could affect the overall experience.

Engineering approach

AR components were enabled only when their functionality was required. Communication features such as chat, touch synchronization and other events were handled through more efficient, event-driven synchronization rather than continuous unnecessary network activity.

What it demonstrates

Runtime feature management, mobile optimization, real-time communication and designing application behaviour around network constraints.

04 / PLATFORM INTEGRATION

Extending Unity with native mobile capabilities

Native Plugins

The problem

Some application capabilities required platform-native behaviour that was not directly available through the Unity application layer.

Engineering approach

Personally developed native Unity plugins, including a sharing plugin for Android and iOS that exposed the platform's native sharing interface to the Unity application.

What it demonstrates

Unity-to-native integration, mobile platform understanding and extending the engine beyond its standard runtime APIs.

05 / MULTIPLAYER

Building real-time multiplayer experiences

Games & Applications

The problem

Multiplayer was a recurring requirement across racing games, FPS games and interactive applications. Different products required different synchronization and state-management needs.

Engineering approach

Worked with Photon PUN, Firebase-based systems and application-specific synchronization flows. Multiplayer systems covered gameplay, player state, interactions, leaderboards and collaborative application behaviour.

What it demonstrates

Real-time systems, network synchronization, multiplayer gameplay and designing interactive applications around shared state.

06 / GAMEPLAY SYSTEMS

From gameplay mechanics to complete game systems

Racing & FPS

The problem

Commercial game projects required more than isolated gameplay features. Racing and FPS projects required gameplay, AI, multiplayer, UI, player interaction and platform-specific behaviour to work together.

Engineering approach

Worked across the game systems required to turn prototypes and individual mechanics into playable multiplayer experiences, including AI opponents, gameplay systems, UI and networking.

What it demonstrates

End-to-end Unity gameplay engineering and the ability to work across interconnected systems rather than isolated features.

Build it. Understand it. Improve it.

I prefer understanding the complete system rather than treating a Unity feature as an isolated piece of code.

That means looking at how content is created, how it reaches the application, how it is loaded, how it interacts with other systems and what happens when the application runs on a constrained device or an unreliable network.

In leadership roles, the same approach extends to architecture, planning, engineering quality, mentoring, delivery and communication with stakeholders.
