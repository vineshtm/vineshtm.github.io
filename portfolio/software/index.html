Engineering in practice

The interesting part
is what happens underneath.

Software rarely exists as an isolated feature. The engineering problems I have worked on often appeared at the boundaries between applications, services, networks, devices, content and users.

01 / SYSTEM BOUNDARIES

Designing how the pieces connect

Architecture

The challenge

Products often involved multiple application layers, third-party services, backend APIs and platform-specific capabilities. A feature could not always be designed in isolation from the rest of the system.

Engineering approach

Participated in architecture discussions and technical decision-making, designed smaller application modules and their interactions, defined technical flows and worked with developers to turn requirements into implementable systems.

What it demonstrates

System thinking, modular design, technical decision-making and the ability to reason about how different components should work together.

02 / CONTENT DELIVERY

Designing around content that does not exist at build time

Creator & Wonder

The challenge

Creator allowed users to work with custom 3D models, images and textures that could not be known when the application was built.

Engineering approach

A content flow was established around uploading assets, transferring them when required and making them available to the application at runtime. The approach considered content delivery, application behaviour and the constraints of the target devices.

What it demonstrates

Runtime content architecture, API integration, asset management and designing application behaviour around dynamic data.

03 / PERFORMANCE

Performance is a system problem

Engage & Remote Assist

The challenge

Mobile applications had to operate with limited memory, storage, processing capacity and network reliability. Performance problems could originate from the interaction between several parts of the system.

Engineering approach

Worked on image compression, lazy loading, local caching, controlled runtime feature activation and more efficient synchronization to reduce unnecessary work and network activity.

What it demonstrates

Performance analysis across application behaviour, memory, storage, network usage and user experience rather than treating optimization as a single isolated task.

04 / REAL-TIME SYSTEMS

Synchronizing the right things at the right time

Multiplayer & Collaboration

The challenge

Multiplayer games and collaborative applications required different forms of shared state, interaction and synchronization.

Engineering approach

Worked with Photon PUN and Firebase-based systems and application-specific synchronization flows covering gameplay state, player interaction, leaderboards, chat, touch interaction and collaborative behaviour.

What it demonstrates

Real-time architecture, synchronization thinking, state management and designing communication behaviour around the needs of the application.

05 / PLATFORM INTEGRATION

Connecting application code with native capabilities

Mobile

The challenge

Cross-platform applications sometimes require capabilities that belong to the underlying operating system rather than the application framework.

Engineering approach

Personally developed native Unity plugins, including Android and iOS sharing functionality that exposed the platform's native sharing interface to the application.

What it demonstrates

Cross-platform thinking, native mobile integration and understanding where application-level code ends and platform capabilities begin.

Engineering philosophy

Build it. Understand it. Improve it.

I prefer understanding the complete system rather than treating a feature as an isolated piece of code.

That means looking at how information moves through the product, how applications communicate with services, how content is delivered, how state is maintained, how devices behave under constraints and where performance or reliability can break down.

In leadership roles, the same approach extends beyond code into architecture, planning, engineering quality, mentoring, delivery and communication with stakeholders.

I started my software engineering career working across multiple mobile platforms before moving deeply into Unity development. Over time, my role evolved from hands-on development into technical leadership while continuing to remain involved in implementation and engineering decisions.

That has shaped how I approach software engineering: understand the complete system, identify the boundaries between components, make practical architectural decisions and keep the implementation maintainable enough to evolve.
